# نقشه اجرای دستیار جامع اختصاصی دانیال ۳.۰

## وضعیت آغاز
- شاخه توسعه: `danial-3.0` (مشتق از `main`؛ بدون تغییر در نسخه تولید)
- افزونه ChatGPT: `daftar-khas-unified` نسخه 2.3.12، خصوصی و در محدوده USER
- وب‌اپ: Next.js 15.5.9 / React 19.1.0
- مخزن داده: Supabase پروژه `jwhyeohqolabcbuwhfon` در منطقه `eu-central-1`، وضعیت مشاهده‌شده `ACTIVE_HEALTHY`
- استقرار Render: سرویس `danial-legal-assistant` روی پلن Free؛ آخرین deployment مشاهده‌شده live است.
- شاخه تولید Render به `main` متصل است؛ توسعه 3.0 فقط در شاخه جداگانه انجام می‌شود.

## یافته‌های ممیزی اولیه
### امنیت
- RLS برای جدول‌های عمومی بررسی‌شده فعال است؛ این موضوع جایگزین آزمون دسترسی بین‌دفترها و نقش‌ها نیست.
- Supabase Auth: قابلیت Leaked Password Protection غیرفعال گزارش شده است. فعال‌سازی آن باید از تنظیمات Auth انجام شود و در این مخزن با تغییر کد حل نمی‌شود.
- مخزن GitHub در زمان ممیزی عمومی بود. خصوصی‌سازی آن از تنظیمات مالک مخزن انجام می‌شود.
- هیچ رمز، کد بازیابی، OTP، توکن یا کلید API نباید در مخزن، گزارش، مهارت یا گفتگو ثبت شود.

### عملکرد پایگاه داده
- هفت سیاست RLS در جداول گفت‌وگوها/پیام‌ها فراخوانی `auth.uid()` را در هر ردیف تکرار می‌کنند؛ migration پیشنهادی این فراخوانی را به شکل init-plan بهینه می‌کند، بدون تغییر predicates.
- دو کلید خارجی فاقد index پوششی گزارش شده‌اند: `project_archive_conversations.import_id` و `slack_integrations.installed_by`.
- ۲۹ index به‌عنوان unused گزارش شده‌اند؛ تا بررسی دوره مصرف و بار واقعی، هیچ index حذف نشود.
- پنج مورد multiple permissive policies گزارش شده‌اند؛ هر اصلاح باید با حفظ محدودیت‌های restrictive و مجوزهای فعلی انجام شود.

### وب‌اپ و تجربه کاربری
- داشبورد فعلی آمار پرونده، موکل، موعد، سند و آرشیو را از پایگاه داده می‌خواند.
- صفحه چت، تاریخچه را با `cache: no-store` دریافت می‌کند؛ درخواست‌های جانبی Slack در بارگذاری اولیه باید از مسیر اصلی چت جدا و غیرمسدودکننده بمانند.
- health endpoint در کد وجود دارد، اما دسترسی مستقیم از ابزار مرور در این نوبت تأیید نشد.
- نصب‌پذیری پایه PWA در manifest تعریف شده؛ آزمون واقعی نصب روی Android/iOS هنوز لازم است.
- OCR خودکار کامل PDF/تصویر در وضعیت فعلی تأیید نشده است؛ استخراج TXT به‌تنهایی OCR محسوب نمی‌شود.

## مراحل و معیار پذیرش
1. **امنیت پایه:** خصوصی‌سازی مخزن، فعال‌سازی leaked password protection، بررسی سیاست‌های RLS، آزمون عدم دسترسی کاربر دفتر A به دفتر B.
2. **بهینه‌سازی DB:** اجرای migration پیشنهادی در محیط staging، بررسی advisorها، اجرای آزمون نقش‌ها و مقایسه query plan؛ سپس تصمیم جداگانه برای indexها.
3. **پایداری وب‌اپ:** بررسی لاگ‌ها، health check، خطاهای ورود و cold start؛ هیچ تغییر پلن یا متغیر محرمانه بدون بررسی و تأیید انجام نشود.
4. **مدیریت پرونده:** تکمیل CRUD طرفین، رویدادهای دادرسی، پیوست‌ها، مجوز پرونده‌ای و گزارش تغییرات.
5. **پردازش اسناد:** صف پس‌زمینه، OCR فارسی، استخراج متن، ثبت نسخه و اتصال قطعی هر سند به پرونده/دفتر؛ اسناد مبهم در صف تطبیق باقی بمانند.
6. **پژوهش قضایی:** جست‌وجوی منابع رسمی، ثبت شناسه و URL منبع، تاریخ دسترسی، نوع رأی/نظریه و وضعیت اعتبارسنجی.
7. **موبایل/PWA:** RTL واکنش‌گرا، تاریخ شمسی نمایشی، ذخیره امن، پیام خطای قابل فهم و آزمون نصب روی دستگاه واقعی.
8. **روبیکا:** فقط پس از احراز API رسمی/بات، محدودیت دسترسی و رضایت مجزا؛ دسترسی بات به پیام‌های خودش به معنی دسترسی به تمام پیام‌های خصوصی حساب نیست.

## قواعد انتشار
- هیچ migration روی پایگاه داده تولید بدون آزمون staging و بررسی rollback اجرا نشود.
- هیچ تغییر مستقیم روی `main` یا deploy تولید در جریان توسعه شاخه 3.0 انجام نشود.
- هر قابلیت با یکی از وضعیت‌های «طراحی‌شده»، «در کد»، «آزمون‌شده»، «مستقرشده» و «تأییدشده در تولید» گزارش شود.
- اطلاعات پرونده، اسناد موکل و داده‌های هویتی نباید در log یا ابزارهای ثالث بیش از حد لازم ارسال شوند.
